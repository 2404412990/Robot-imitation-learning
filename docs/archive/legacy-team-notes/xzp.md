# 2026.5

## 工作主题
学习项目整体流程 / 阅读代码 / 数据分析 / 配合联调

## 工作内容

五月主要在补基础。

之前对项目整体其实没完全摸清楚，大概知道是「WHAM 估计人体姿态 → GMR 重定向到机器人 → Unity 里回放」这一套，但具体每一步在做什么、谁负责哪一段，并没有真正串起来。这个月花了不少时间在看仓库、看代码、看文档。

### 1. 看 WHAM / GMR 的资料

五月初把 WHAM 仓库 README、几个 demo 都看了一遍，整理了一个小笔记：

- 输入：视频或摄像头画面
- 中间：用 ViTPose 提取 2D 关节点，再用网络恢复 3D 人体姿态，输出 SMPL 参数
- 输出：SMPL 的人体 mesh 和参数

GMR 把 SMPL 参数映射到机器人关节。它通过 smplx_to_*.json 配置文件描述人体关节与机器人各个 IK 约束之间的对应关系，不同机器人使用各自的映射配置。

这部分只是停留在“能看懂输入输出”，算法内部没去抠。

### 2. 熟悉 Unity RL Playground / 格物平台

格物平台是基于 Unity RL Playground 改的，这周把 Assets/Imitation/ 大致过了一遍：

- G1mimicAgent 是核心回放脚本，从 CSV 读数据，写到 ArticulationBody 的 xDrive.target
- H1mimicAgent 结构和 G1 类似，但关节定义不一样
- StartInput 是 UI 那边的入口
- dataset 目录按机器人名称分目录存放离线 CSV

### 3. CSV 动作数据格式分析

为了弄清楚 CSV 里到底存的是什么，我把 lzy 跑出来的一个 my_motion.csv 拉出来，用文本编辑器打开看：

```
root_pos_x, root_pos_y, root_pos_z, root_rot_x, root_rot_y, root_rot_z, root_rot_w, dof_0, ..., dof_28
```

G1 的每一帧共有 36 个数值：前 3 列是根节点位置，接着 4 列是根节点四元数，后面 29 列是各个关节角度。

把每一列对照着 G1 的关节定义文档看了一遍，确认 29 个 DOF 都能对得上，没有缺失或者重复的列。

然后试着改了几个数：
- 把 root_pos_y 整体抬高 0.3 → 机器人整体飞起来
- 把 knee 那列整体乘 1.5 → 膝盖弯得更厉害
- 删掉几行 → 动作变短，没有报错

改完保存，重新打开 Unity，回放窗口里能看到对应的变化。这下基本确定 CSV 里每一列起什么作用了。

### 4. 配合联调：实时抽搐问题

五月有一次 zjl 反映实时联调时机器人抽搐严重。我这边主要是从 CSV 数据的角度去排查：

- 离线 CSV 回放：动作连续，没有抽搐
- 实时 CSV 回放：每隔几帧会出现一次“跳”，机器人突然瞬移

怀疑过实时 CSV 写得不规范，比如同一行被覆盖写了多次。后来拿 lzy 那边的脚本单独跑了一段时间，把实时生成的 CSV 拷贝出来逐帧看，数据本身是连续的，没有重复。

最后定位下来不是 CSV 内容的问题，而是 Unity 消费数据的速度快于 Python 管线生成新行的速度。组长 lzy 后续通过对齐两端帧率、调整 Unity 读取节奏并增加帧间插值进行修正。我跟着观察了一段时间，抽搐明显好转，但偶尔还会闪一下，没有完全消失。

## 问题

1. **身体腾空**：五月没有实质推进，等 zzh 的物理约束方案。
2. **WHAM 内部算法**：只是看懂了输入输出，RNN/LSTM 时序建模部分没有深入研究。
3. **实时抽搐**：参与数据层面的排查，确认主要是 CSV 生产与 Unity 消费速度不匹配；具体修复由 lzy 在主版本中完成，我这边没有修改核心管线。

## 小结

五月基本没做什么新功能，主要是在看代码、看文档、分析数据、跟着排查问题。算是把整个项目的“地图”大致摸清了，知道哪一块是谁在做，自己负责的那一段（CSV 回放接入）目前是通的，剩下的就是配合联调和等别人把别的模块搞定。
